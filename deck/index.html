02 · 核心理论
SP 矩阵：从营销学战略定位到饮食定位
经典的 SP（Sweet Point）矩阵用「竞争强度 × 市场地位」划分战略象限。我们把它迁移到了饮食选型上

X营养密度 —— 对应「吸引力」

(蛋白质g + 碳水g) ÷ (热量 ÷ 100)

每 100 kcal 能换来多少克营养。
用密度而非绝对值，消除了「大份餐热量高所以显得更差」的量纲偏差。

Y钠负担 —— 对应「强度」

钠mg ÷ (热量 ÷ 100)

每 100 kcal 要背多少毫克钠。
这是中式快餐里最难回避的取舍维度。

四象限语义

主力区 ⭐
高营养密度 + 低钠负担
控卡期首选，建议常点
双刃区
高蛋白但高钠
增肌日可吃，控卡日限一次
解馋区
低营养密度但钠负荷高
想吃就吃，别当正餐
填充区
低钠但也缺营养
饱腹陷阱，减脂期避开

03 · 目标计算
第一步：把「我该吃多少」算清楚
Mifflin-St Jeor 基础代谢 → FAO/WHO 活动系数 → ACSM 三大营养素配比

计算链路

步骤公式 / 依据
基础代谢 BMRMifflin-St Jeor（填了体脂率则切 Katch-McArdle 修正）
总消耗 TDEEBMR × PAL 活动系数（1.2 / 1.375 / 1.55 / 1.725 / 1.9）
目标热量TDEE × 模式系数（减脂 0.80 / 维持 1.0 / 增肌 1.12）
三大营养素ACSM 建议配比 × 目标热量，体脂率参与修正
钠上限WHO 全日 2000 mg 口径 × 目标热量密度

实测输出 25岁男 · 175cm · 70kg · 轻度活动 · 减脂

1712基础代谢 kcal
144 g蛋白质
246 g碳水
58 g脂肪
2000 mg钠上限

04 · 核心算法
第二步：结构角色模型 + 多目标约束求解
不是从 160 个单品里做笛卡尔积，而是先定义一餐该有的角色结构

角结构角色模型

每个单品先归入 主餐 / 小食 / 饮品 / 甜点 四个角色，再按角色组合。 这样杜绝了「两个雪冰 + 一杯奶昔」这种荒谬组合 —— 一餐必须有明确的角色分工。

主餐恰好 1 份饮品恰好 1 份 小食 ≤ 1甜点 ≤ 1

硬硬约束

主餐热量带占本餐 40%–85%
角色热量上限小食 max(45%, 400kcal) · 饮品 max(25%, 250kcal)
配菜质量下限≥6g 蛋白 或 ≥120 kcal
控卡期禁甜点减脂 / 塑形模式直接排除

06 · 工程难点
难点一：菜单 56% 是套餐，怎么给它算 SP 坐标？
官方营养表只收录单品，「三件套 / 四件套 / 分享餐」在表里查不到

解解法：拉明细，按热量加权聚合

用 query-meal-detail 拿到套餐每一轮的组成， 只取已选中的那个选项（isDefault=1 或 selectedQuantity>0）， 同一单品只计一次，再按热量加权聚合出这个套餐自己的营养画像与 SP 坐标。

只取选中项同单品去重按热量加权

坑踩过的坑

一开始把所有轮次的所有选项累加起来，套餐热量算出 3222 kcal —— 相当于吃了四顿。 根因是没做「已选中」过滤，也没做单品去重。

五五级名称匹配

1 · 全名精确「巨无霸」→ 命中
2 · 去后缀「巨无霸三件套」→ 去「三件套」
3 · 去前缀修饰「龙焰鸡腿堡」→ 「鸡腿堡」
4 · 双向包含取最长命中，排除「无糖」误配
5 · 品类回退新品按同品类中位单品近似

覆盖率提升

31/87改造前 · 35%
→
86/98改造后 · 88%

未被营养表收录的新品，按同品类中位单品近似并显式标注「新品估算」，不假装精确。

06 · 工程难点
难点二：官方接口的五个真实陷阱
全部来自实际联调，已整理进 MCP_INTEGRATION.md 供后来者参考

1计价契约字段名

契约是 productCode + quantity，传成 code/count 不报错，只是静默返回全 0 价格，极难排查。

2价格单位双口径

菜单接口的 currentPrice 已是元（"29.9"）， 计价与下单返回的却是分（2990）。统一除以 100 会让 29.9 元显示成 0.3 元。

3营养表是伪表格

list-nutrition-foods 的 data 不是 JSON，而是 [160]{字段列表}: 加每行一条的自定义文本格式，需要专用解析器。

4返回结构不一致

query-my-coupons 返回 dict（{coupons:[...]}）， 而 available-coupons 返回 list。统一按 list 取会让卡包恒空。

5门店状态是真实业务状态

部分门店当日已打烊，接口会返回「门店可能已关闭或不在营业时间」。 这不是 bug —— 前端需要给出可读提示，而不是空白页或崩溃。

08 · 总结
项目亮点与适用边界

亮四个核心亮点

理论创新SP 矩阵从营销学迁移到饮食选型，用密度指标消除量纲偏差
算法扎实结构角色模型 + 多目标约束求解 + 局部搜索，产出真正可执行的一餐
闭环完整营养 → 选店 → 领券 → 下单 → 记录，五个环节全部打通官方 MCP
数据真实160 条营养数据 + 98 个菜单条目，覆盖率 88%，无一是编的

技技术栈

Python 3.10+FastAPIuvicorn SQLite原生 CanvasMCP Streamable HTTP WorkBuddy Skill

界适用边界（重要）

· 输出仅供参考，不构成医疗、营养或其他专业建议
· 营养数据来自官方接口，新品可能未收录（已标注「新品估算」）
· 钠上限按 WHO 全日口径，不摊到单餐 —— 分摊会导致几乎所有套餐判超标
· 门店状态实时变化，部分门店可能已打烊
· 餐品价格与供应以麦当劳官方渠道实时结果为准

隐隐私与安全

Token 只从环境变量读取，不入代码库；健康档案（体重、饮食记录）仅存本地 SQLite，不上传任何服务器； 所有 MCP 调用经统一出口，便于审计。

【800 字版 · 完整正文】

麦当劳营养膳食专家
身材管控期也想吃麦当劳？这个专家会帮你根据每日消耗搭配麦麦套餐。

一、痛点：四个「不知道」

控卡期走进麦当劳，真正的障碍从来不是「不知道吃什么」，而是四个具体的「不知道」。

· 不知道该吃多少。算出全天目标 1841 kcal，却不知道一餐该占多少。
  按全天目标的 100% 去凑一餐，会点成两顿的量。
· 不知道该点哪个。门店菜单接近 100 个条目，看得见的热量标签为零。
  只能靠图片和名字猜，猜错就是一天超支。
· 不知道哪套搭得值。「三件套」看不出装了什么，勾完才发现全是糖和油，
  钠、蛋白、脂肪一个都控制不住。
· 不知道自己吃过了什么。吃完就忘，热量缺口无从谈起，
  体重在涨却不知道是哪几顿造成的。

二、方法论：SP 矩阵从营销学迁移到饮食选型

经典 SP（Sweet Point）矩阵以「竞争强度 × 市场地位」划分战略象限，是营销学的经典工具。
本项目做了语义转译，映射为两个营养维度：

  X 轴（吸引力）→ 营养密度 = (蛋白质g + 碳水g) ÷ (热量 ÷ 100)
  Y 轴（强度）  → 钠负担   = 钠mg ÷ (热量 ÷ 100)

为什么用密度而非绝对值？这是本项目最关键的一个设计决定。若用绝对蛋白含量，
大份餐会因为热量高而显得「更差」；若用绝对钠含量，小份餐会因为总量低而显得「更安全」
——都是量纲偏差。改用「每 100 kcal」的密度口径后，不同份量的餐品才具备可比性。

四象限语义：
· 主力区 ★（高密度 + 低钠）—— 控卡期首选，建议常点
· 双刃区（高密度 + 高钠）—— 高蛋白但高钠，增肌日可吃，控卡日限一次
· 解馋区（低密度 + 高钠）—— 想吃就吃，别当正餐
· 填充区（低密度 + 低钠）—— 饱腹陷阱，减脂期避开

动态阈值：分割线不是写死的常数，而是取全样本的 中位数×0.6 + P75×0.4，
避免极端单品（极端高钠或极端低钠）把分割线拉偏。
实测 156 个有效样本下，阈值落在 x = 16.17、y = 116.83，
四象限分布为：主力区 47、解馋区 46、填充区 53、双刃区 10。

贴合度：每个餐品相对目标点的贴合度 fit = max(0, 1 - dist/1.4)，其中目标点由用户
身体档案推导。档案一变，目标点移动，全矩阵贴合度实时重算——
这让「矩阵」从一个静态图变成一个真正可推荐的工具。

三、目标计算：全天与单餐必须分开

链路：Mifflin-St Jeor 基础代谢（填写体脂率则切 Katch-McArdle 修正）
→ × FAO/WHO 活动系数（1.2 / 1.375 / 1.55 / 1.725 / 1.9）
→ × 模式系数（减脂 0.80 / 维持 1.0 / 增肌 1.12）
→ 全天目标热量 → ACSM 三大营养素配比，
同时按 WHO 全日 2000 mg 口径给出钠上限。

实测（25 岁男 / 175cm / 70kg / 轻度活动 / 减脂）：
  基础代谢 1712 kcal
  全天目标 1841 kcal
  蛋白质 / 碳水 / 脂肪 = 144 g / 246 g / 58 g
  钠上限 2000 mg（全日口径）
  单餐目标 626 kcal（= 1841 × 34%）

关键设计：全天目标与单餐目标必须分开。单餐份额固定 34%，这是后续所有约束的基准线。

四、选餐求解：结构角色模型 + 多目标约束

不是从 160 个单品做笛卡尔积（那是天文数字级的组合，且大部分毫无意义），
而是先定义结构：

· 结构角色模型：每个单品归入 主餐 / 小食 / 饮品 / 甜点 四角色，再按角色组合。
  主餐恰好 1 份、饮品恰好 1 份、小食 ≤ 1、甜点 ≤ 1。
  这从根本上杜绝了「两个雪冰 + 一杯奶昔」这类荒谬组合。
· 硬约束：主餐热量占本餐 40%–85%；
  角色级热量上限取 max(比例, 绝对值)（小食 max(45%, 400kcal)、饮品 max(25%, 250kcal)）；
  配菜质量下限 ≥6g 蛋白 或 ≥120 kcal；减脂/塑形模式直接排除甜点。
· 六维加权：热量 26% · 蛋白 28% · 碳水 13% · 脂肪 11% · 钠 14% · 饱腹 8%。
· 局部搜索：在初始解上反复做「加一份 / 减一份 / 换一份」三种邻域操作，
  迭代至得分不再提升；最后做多样性去重，保证返回的三个方案彼此有区分度。

实测输出（同前述档案，单餐目标 626 kcal）：

  方案一 · 最优贴合  719 kcal  占全天 39%  蛋白 44 g  钠 1981 mg
    板烧鸡腿堡 + 麦麦脆汁鸡琵琶腿 + 无糖可乐中杯
  方案二            611 kcal  占全天 33%  蛋白 43 g  钠 1993 mg
    麦辣鸡腿堡 + 蒜了吧风味脆汁鸡 + 无糖可乐中杯
  方案三            555 kcal  占全天 30%  蛋白 46 g  钠 1802 mg
    双层吉士汉堡 + 蒜了吧风味脆汁鸡 + 无糖可乐中杯

三套方案的饮品位全部落在零卡选项上——这不是巧合，
而是角色约束与钠维度权重共同作用的结果。

五、工程难点一：菜单 56% 是套餐，怎么算它的 SP 坐标？

官方营养表只收录单品，「三件套 / 四件套 / 分享餐」在表里查不到。
解法是拉套餐明细、按热量加权聚合：

  1. 用 query-meal-detail 拿到套餐每一轮的组成；
  2. 只取已选中的那个选项（isDefault == 1 或 selectedQuantity > 0）；
  3. 同一单品只计一次（跨轮次去重）；
  4. 按热量加权聚合出该套餐自己的营养画像与 SP 坐标。

踩过的坑：最初把所有轮次的所有选项都累加起来，某套餐热量算出 3222 kcal——
相当于吃了四顿。根因是没做「已选中」过滤，也没做单品去重。

名称匹配做了五级降级：全名精确 → 去括号/套餐后缀 → 去前缀修饰 →
双向包含（取最长命中，排除「无糖」这类误配）→ 品类关键词回退。

覆盖率：31/87（35%）→ 86/98（88%）。
未被营养表收录的新品，按同品类中位单品近似，并显式标注「新品估算」，不假装精确。

六、工程难点二：官方接口的五个真实陷阱

全部来自实际联调，已整理进 MCP_INTEGRATION.md：

  1. 计价契约字段名 —— 是 productCode + quantity，传成 code/count
     不报错，只是静默返回全 0 价格，极难排查。
  2. 价格单位双口径 —— 菜单接口 currentPrice 已经是元（"29.9"），
     但计价与下单返回分（2990）。统一除以 100 会让 29.9 元显示成 0.3 元。
  3. 营养表是伪表格 —— list-nutrition-foods 的 data 不是 JSON，
     而是 [160]{字段列表}: 加每行一条的自定义文本格式，需要专用解析器。
  4. 返回结构不一致 —— query-my-coupons 返回 dict（{coupons:[...]}），
     而 available-coupons 返回 list。统一按 list 取会让「我的卡包」恒为空。
  5. 门店状态是真实业务状态 —— 部分门店当日已打烊，
     接口返回「门店可能已关闭或不在营业时间」。这不是 bug，
     前端需要给出可读提示，而不是白屏或崩溃。

七、架构与产品形态

依赖方向严格单向：表现 → 服务 → 领域 → 集成。

· 表现层 web/index.html —— 单文件原生前端，零第三方依赖、零 CDN。
  SP 散点图 / 折线图 / 象限条形图全部 Canvas 原生绘制。
  五个视图：建档 · SP 矩阵 · 套餐推荐 · 门店点餐 · 健康可视化。
· 服务层 scripts/server.py —— FastAPI + uvicorn，14 个 REST 接口。
  只负责协议适配、价格口径归一、字段名归一、套餐聚合、明细缓存。
· 领域层 —— nutrition_engine.py（档案校验 / BMR / TDEE / 三大营养素）、
  sp_matrix.py（四象限 / 动态阈值 / 贴合度）、
  combo_solver.py（结构角色 / 多目标约束求解 / 局部搜索）。不感知 HTTP。
· 集成层 scripts/mcp_client.py —— 唯一的 MCP 出口，Streamable HTTP 客户端，
  自带限流 / 重试 / 退避。健康档案走 scripts/health_store.py
  （SQLite 三表分离，本地存储，不上传）。
· 底层 麦当劳官方 MCP Server（https://mcp.mcd.cn）—— 35 个官方工具。

性能优化：套餐明细聚合是最大开销（一次菜单要拉 30+ 个套餐明细）。
加入进程内 _detail_cache（键为 (store_code, meal_code, order_type, be_type, be_code)）后，
菜单接口从 18.6 s → 0.56 s（冷启动）/ 0.65 s（缓存命中）。

八、亮点、边界与隐私

四个核心亮点：
  1. 理论创新 —— SP 矩阵从营销学迁移到饮食选型，用密度指标消除量纲偏差，
     形成可解释、可复算的选餐依据。
  2. 算法扎实 —— 结构角色模型 + 多目标约束求解 + 局部搜索，
     产出真正可执行的一餐，而非「一堆候选里排序」。
  3. 闭环完整 —— 营养 → 选店 → 领券 → 下单 → 记录，五个环节全部打通官方 MCP，
     不是孤立的计算器。
  4. 数据真实 —— 160 条营养数据 + 98 个菜单条目，SP 覆盖率 88%，无一条是编的。

适用边界（重要，必须明确）：
  · 输出仅供参考，不构成医疗、营养或其他专业建议。
  · 营养数据来自官方接口，新品可能未收录（已显式标注「新品估算」）。
  · 钠上限按 WHO 全日口径，不摊到单餐 —— 摊到单餐会导致几乎所有套餐被判超标。
  · 门店状态实时变化，部分门店可能已打烊。
  · 餐品价格与供应以麦当劳官方渠道实时结果为准。

隐私与安全：
  · MCP Token 只从环境变量读取，不入代码库（.env 已被 .gitignore 排除）。
  · 健康档案（体重、饮食记录）仅存本地 SQLite，不上传任何服务器。
  · 所有 MCP 调用经统一出口，便于审计。
